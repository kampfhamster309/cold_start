# cold_start — Technology Stack Recommendation

> Companion to [01-overview.md](01-overview.md). This document picks a concrete stack for the features described there and feeds directly into [03-architecture.md](03-architecture.md). Recommendations are decisive by design — where an alternative was seriously considered, it's named along with why it lost, but each section ends with one answer, not a menu.

## 1. Frontend

**Pick: React + Next.js (App Router), TypeScript.**

Rationale:
- The onboarding hub is UI-heavy in a way that benefits from a mature component/ecosystem story: dashboards (repo activity, "who to ask"), a rich-text/Markdown WYSIWYG editor for non-technical doc editors, diff/history views, and search UI.
- Rich-text editing is the one non-negotiable UI requirement (G4/5.2 — non-technical staff must not need Markdown-source or git familiarity). The React ecosystem has the most mature options here (TipTap/ProseMirror, Slate), with better maintenance and plugin coverage than competing framework ecosystems.
- Next.js gives file-based routing, easy SSR/streaming for dashboard-style pages, and a well-understood self-hosted deployment story (`next build` + standalone output in a single container) — important since self-hosted is the primary deployment target (§8).

Top alternative considered: **SvelteKit.** Lighter runtime and less boilerplate. Rejected, but not for the reason "thinner editor ecosystem" implies: TipTap (the leading ProseMirror-based editor) is framework-agnostic at its core and does run on Svelte, so the editing engine itself isn't the gap. The real gap is narrower — TipTap's Svelte bindings (`svelte-tiptap`, `Tipex`) are third-party/community-maintained rather than official first-party integrations, and typically lag the React binding in features and stability. More decisively, **Lexical** (Meta's actively-developed editor, TipTap's strongest competitor) is React-native by design with no official Svelte support at all. Combined with React's larger team-familiarity/hiring surface, that's what tips this decisively toward React — not a shortage of Svelte-compatible editing engines that doesn't actually exist.

## 2. Backend

**Pick: Go, using a lightweight HTTP framework (e.g., `chi` or `net/http` + a thin router) rather than a heavyweight batteries-included framework.**

Rationale:
- Two of the hardest technical requirements — code-repository ingestion (commit/blame walking at potentially non-trivial scale, §5) and the non-code doc store's git internals (§4) — are both best served by Go's git tooling: `go-git` (pure-Go, embeddable, no external process) for the doc store, and the native `git` CLI shelled out from Go for ingestion-side blame/churn analysis. Building both around one language avoids splitting git-handling logic across two runtimes.
- Single static binary output is a strong fit for the self-hosted docker-compose target (§8): small images, no `node_modules`-class dependency bloat, straightforward cross-compilation.
- Good concurrency primitives for background ingestion workers (webhook consumers + scheduled polling, §5) without needing a separate job-queue service at MVP scale.

Top alternative considered: **Node.js/TypeScript (NestJS).** Same language as the frontend (reduces context-switching for a small team), and the CRUD ecosystem (Prisma, NestJS modules for auth/RBAC) is more batteries-included than Go's, which matters for the fairly standard onboarding-planner CRUD surface (§5.3 of the overview). Not chosen: the ingestion and doc-store work is the technically riskiest part of this project, and Go's git tooling (`go-git`, `go-github`, `go-gitlab`) is materially stronger than the JS equivalents (`isomorphic-git` is functional but slower and less complete for the kind of history walking ingestion requires). The CRUD-ecosystem gap is real but small and closable with a good Go ORM/query builder (e.g., `sqlc` or `ent`); the git-tooling gap in the other direction is not something a CRUD framework can compensate for.

## 3. Primary database

**Pick: PostgreSQL.**

Rationale:
- Handles all standard relational data: users/roles, repo connections, onboarding plan templates and per-hire progress, ingested commit/expertise metadata.
- JSONB support covers the overview's "structured content types where useful" requirement (5.2) — team pages, processes, and FAQs can share one storage shape with type-specific JSONB payloads rather than needing per-type tables.
- Doubles as the MVP search backend (§7) via built-in full-text search, avoiding a second stateful service early on.

Top alternative considered: **MySQL.** Comparable for the plain relational workload, but weaker JSONB/GIN-index support, and its `FULLTEXT` indexes are materially weaker than Postgres's `tsvector`/`tsquery` for §7's needs (thinner ranking, no comparable stemming-dictionary story) — not "no story," just a worse one. Not chosen.

## 4. Non-code documentation versioning backend

This is the highest-risk decision in the stack, and the overview frames it explicitly as an open question (§8: "how much of non-code doc versioning needs to be a *real* git repo... vs. an internal version history model that merely behaves like one"). Three realistic options, plus the recommendation.

### Option A — Embed Gitea/Forgejo as the storage backend, build a web editor on its API

**Rejected**, on tighter grounds than "extra service to run":

- **The identity-system cost is a real fork, not an unavoidable tax.** You could run Gitea/Forgejo behind a single service account and enforce all permissions in the app layer — same model as Option B — which avoids provisioning/syncing a second user directory. But doing that throws away the actual reason to embed a git forge in the first place: its native per-user ACLs, PR/commit attribution, and branch protection all require real per-user accounts to mean anything. So the honest tradeoff is "sync identities and get Gitea's collaboration features" vs. "skip the sync and pay Gitea's operational cost for a service you're using as a plain git storage daemon." Neither branch is attractive, and the second one — the one that would actually satisfy 5.2/G4's independence requirement — gets none of Gitea's differentiated value.
- **The operational cost is real but smaller than "a second full service" implies.** Both Gitea and Forgejo ship as a single Go binary with an embedded-SQLite option, so this isn't a heavyweight addition to the docker-compose topology. The genuine cost is narrower: a second codebase's CVEs and upgrade/migration cadence to track on an ongoing basis (git forges have had real path-traversal/RCE-class findings historically) — worth naming precisely rather than hand-waved as general "operational overhead."
- **A concrete technical blocker: no atomic multi-file commits via the API.** Gitea/Forgejo's content API (`repoCreateFile`/`repoUpdateFile`/`repoDeleteFile`) commits one file at a time — there's no endpoint for a single commit spanning multiple file changes. The doc-store's structured content types (front-matter-driven pages, potential companion files) and the "one doc save = one commit" model this stack assumes both need atomic multi-blob commits. Under Option A that means either multiple sequential commits per save (breaking the atomicity/rollback story the doc-store is supposed to guarantee) or dropping to the git smart protocol directly — which forfeits the reason to embed a forge instead of just managing the repo yourself. `go-git` gives direct tree/blob construction, so this isn't a constraint under Option B. This is the deciding factor, not the operational-overhead framing alone.

Note for "revisiting later": this is cheaper than it sounds, *because* Option B's repo is a real repo. If Phase 2+ wants true collaborative git workflows (protected branches, PR-style doc review, external git-protocol access), a forge can be pointed at the existing bare repo path later with no data migration. If/when that happens, prefer **Forgejo over Gitea**: Forgejo forked from Gitea in 2022 specifically over governance (Gitea is now company-backed/open-core; Forgejo is non-profit-governed under Codeberg e.V.) and is the safer long-term dependency to bolt onto infrastructure you already trust.

### Option B — In-process git library managing a bare repo directly (no separate git server)

**Recommended.** Specifically: **`go-git`**, operated directly by the Go backend against one or more bare repositories on a persistent volume.

- Every doc save is a real git commit (blob/tree/commit/ref update) executed as a function call inside the request that handles the edit — no external process, no network hop to a forge API.
- Permissions are owned entirely by the app's own user/role model (§6), which by construction satisfies "independent of the main code host's account system" — there's no second identity system to reconcile at all, since there's no second service.
- History, diff, and rollback (5.2's explicit requirement) are native git operations, not something built on top of an abstraction — `git log`, `git diff`, revert-equivalents map directly to library calls.
- The repo is still a *real* repo on disk: exporting it for portability is a `git bundle` away, and a read-only smart-HTTP git endpoint could be bolted on later without a data migration, since the underlying storage never changes.
- Fits the docker-compose self-hosted target with zero extra services — it's a volume, not a container.
- Pure Go (no cgo) keeps builds and cross-compilation simple, which matters for a small self-hosted single-binary deployment.

Costs accepted deliberately: the team has to build the edit→commit plumbing (mapping page saves to blob/tree writes), handle concurrent-edit conflicts at the app layer (no server-side branch/PR machinery to lean on), and run periodic repack/GC (not automatic with `go-git`; solvable by shelling out to `git gc` on a schedule, or via `go-git`'s partial repack support). These are bounded, well-understood problems for repo sizes in the range this feature actually needs (a company handbook/wiki, not a code monorepo) — nowhere near where `go-git`'s known performance ceiling would bite.

### Option C — Database-backed revisions table that behaves git-like

**Rejected.** Simplest to build (one database, transactional consistency, trivial permission checks, no git internals needed), but it doesn't satisfy what the overview explicitly asks for: 5.2 says "Full history/diff/rollback, since it's **git-backed underneath**" — not "git-like." A revisions table is a parallel reimplementation of a subset of git's data model, and every future git-native feature request (branch-per-draft, PR-style review of doc edits, real export) would mean re-deriving git rather than reusing it — with a painful migration if real history needs to be backfilled into an actual repo later. The effort saved today is effort re-spent later, at a worse time. (Prior art like Outline.md's Postgres-only revision history shows this pattern is viable for a *general wiki product*, but Outline doesn't promise "git-backed" as a stated feature the way this project's vision does — the bar here is self-imposed by the overview, not by wiki norms generally.)

**Decision: Option B.** One or more `go-git`-managed bare repositories, owned entirely by the app, no separate git server process, no second identity system.

## 5. Code-repository ingestion

**Pick: hybrid — hosting-provider APIs for metadata, local clone for blame/churn (full clone, not shallow), polling-primary with webhooks as an opt-in freshness upgrade where network reachability allows it.**

- **Metadata (commits list, PR/review/approval data, contributors):** pulled via each host's REST/GraphQL API. This isn't optional — PR review/approval data generally doesn't exist in the git object graph at all (GitHub/GitLab store it in their own databases), so "who to ask" signals derived from review activity require the API regardless of how much is done via local clone.
- **Blame and code-churn analysis (5.1):** computed from a **local clone**, using the native `git` CLI shelled out from the ingestion worker — not `go-git`. This is still the one place the stack intentionally reaches for the system git binary instead of the pure-Go library: computing repo-wide blame/churn via hundreds of per-file API calls would burn through host rate limits fast and is materially slower than local `git log --stat` / `git blame`, and `go-git`'s blame/log performance lags the native binary on real code histories. **The clone must be full-depth for blame, not shallow.** `git blame` on a shallow clone can't see past the fetch boundary — any line whose true last-touching commit predates that boundary gets attributed to a synthetic "grafted" commit instead of its real author, and Git's own documentation warns against relying on blame/log over shallow history for exactly this reason. That failure mode lands precisely on the case both consumers of this data care about: a file untouched for a long time is the one most likely to have its real last-touching commit fall outside a shallow window, so a shallow clone would silently degrade the "who to ask" signal (Phase 0) exactly where it matters most, and the same accuracy gap would undermine doc-staleness detection (Phase 1, G3 — layered on this same blame/churn data once repo-doc content ingestion exists to compare it against, see [04-open-items.md](04-open-items.md)) even more directly. Recency/churn analysis (`git log --stat` over a bounded recent window) doesn't have this problem and could use a shallower fetch if clone cost ever becomes real — but at this project's stated scale (a handful of connected repos, not monorepo-scale), that optimization isn't earned yet, so **MVP uses full clones** for both. If clone size becomes a genuine constraint later, prefer deepening on demand (`git fetch --deepen=N` when a blame request crosses the current boundary) over a flat `--depth=N`, since that preserves accuracy instead of trading it away. These clones are read-only, ephemeral (scratch volume, safe to wipe/re-fetch on schedule), and never treated as a source of truth — the host repo remains authoritative.
- **Update mechanism:** **polling is the default, not a backstop** — it's the only mechanism guaranteed to work with zero extra infrastructure. Webhook delivery is an outbound POST from the code host to a URL the app exposes; for a cloud-hosted host like GitHub.com, that requires the cold_start instance to have a publicly reachable endpoint (or a relay/reverse-proxy in front of it, per GitHub's own guidance for delivering webhooks to private systems). Since the deployment target (§8) is self-hosted and often chosen specifically to stay off the public internet, that reachability can't be assumed — for those deployments, webhooks simply never arrive, not "arrive late." **Webhooks are therefore an opt-in freshness upgrade**, enabled when the operator either exposes an inbound endpoint or runs a relay, layered on top of always-on polling — not a primary path with polling as a fallback. The one case where "webhook-first" holds without caveats is a self-hosted code host (GitLab/Gitea) running on the *same* internal network as the app: that's a same-network hop, not internet delivery, so reachability is a non-issue there. Poll frequency is still bounded by API quota (frequent polling burns quota, infrequent polling reintroduces staleness) — that tradeoff is unchanged, it's just now explicitly the primary mechanism to tune rather than a rarely-exercised backstop.
- **Which hosts first: GitLab self-managed, not GitHub.** Revised from an earlier GitHub-first pick, which didn't actually fit this project's own priorities. Two independent reasons converge on GitLab: (1) for the enterprise segment this product targets — a company with real onboarding pain investing in internal tooling, not a two-person shop — GitLab self-managed is the standard self-hosted code host, whereas GitHub's self-hosted offering (Enterprise Server) is comparatively rare; and (2) self-hosted GitLab running on the *same internal network* as cold_start is exactly the deployment shape where the webhook-reachability problem (above) and the Caddy ACME-reachability problem (§8) both disappear by construction — no public ingress, no DNS-01 plugin, no relay. GitHub.com is the case that *introduces* those problems, not one that sidesteps them, so building it first meant validating the ingestion pipeline against the deployment shape this project explicitly isn't targeting first. GitLab's API (REST v4 + GraphQL) covers everything ingestion needs — commits, MR/approval data, contributors — with no capability gap that would force GitHub first on technical grounds. Ingestion is still built behind an internal `RepoProvider` interface from day one, so GitHub.com (still the largest host overall, and plenty of companies self-hosting internal tools keep code on GitHub Cloud) and generic self-hosted git (clone-only, no API — metadata derived purely from local history) can follow in Phase 1 without reworking the pipeline; GitLab is just the one validated first. Bitbucket remains explicitly out of scope — not named in the overview's Phase 0/1.

Top alternative considered: **clone-and-analyze everything locally, skip provider APIs entirely.** Rejected for the reason above — review/approval data isn't derivable from git history alone, so API dependency isn't avoidable; the design choice is only about *minimizing* API volume by pushing bulk history analysis to local clones, not eliminating API use.

## 6. Auth / permissions

**Pick: app-owned user/role table in Postgres as the source of truth, OIDC/SSO as the primary login path, magic-link-only (no standalone local password) as the fallback for accounts outside the company IdP.**

- A first-class user table in the app's own database is required regardless of anything else, since doc-store permissions must be independent of the main code host's account system (G4, 5.2) — this is not satisfied by "Sign in with GitHub/GitLab" alone.
- **OIDC (and SAML if the target company's IdP requires it) as the primary login method**, delegating to whatever identity provider the company already runs (Okta, Azure AD, Google Workspace, Keycloak, etc.) — standard practice for a self-hosted internal tool and avoids the app owning password security for the users who go through it.
- **Magic-link (email-only), not standalone local username/password, as the fallback** for non-engineering staff who may not be provisioned in the main SSO tenant (contractors, People/HR staff at companies without formal SSO) — directly serving G4, with two corrections to the original pick:
  - **No standalone password option.** OIDC coexisting with a separately-registerable local password is the textbook precondition for the **Classic-Federated Merge Attack** (documented by Microsoft MSRC and studied at scale in "Pre-hijacked Accounts: An Empirical Study of Security Failures"): an attacker registers a local account under the victim's real corporate email before the victim's first SSO login; if the app later links accounts by email match, the attacker keeps standing, silent access. Magic-link-only removes this precondition almost entirely, because every login re-verifies control of the inbox by construction — there's no password-only signup path an attacker can complete without ever touching that inbox. It also means the "avoids owning password security" claim above is now literally true rather than partially true: no hashing, no lockout policy, no breach-password checking, no password-security subsystem to own at all.
  - **Explicit anti-merge and session rules, not left implicit.** Even with magic-link-only, an OIDC login arriving later for an email that already has a magic-link account must never be **silently auto-merged** by email match alone — require an explicit confirmation step (e.g., a one-time confirmation link to the existing account's email) before linking. Any account-recovery-equivalent event (e.g., re-issuing access after a suspected compromise) must invalidate existing sessions for that account, closing the related "unexpired session identifier" variant from the same research.
  - **New stack dependency this introduces: outbound transactional email.** Magic-link delivery has a hard dependency on sending email that wasn't previously listed anywhere in this stack — added to the deployment topology and summary table below. Any SMTP-compatible relay/provider works; this doc doesn't pin a specific vendor since it's an operator-supplied credential (self-hosted deployments typically point this at whatever mail relay the company already has), not a service this stack needs to run itself.
- **RBAC** at MVP: viewer / editor / admin roles per the overview's Phase 0 (5.2, "Suggested Phasing"). Modeled from day one as `(user, role, resource_type, resource_id)` grant tuples rather than a single global role per user or a bare `(user, role, scope)` triple — the latter was the original design here, but a single undifferentiated `scope` column can't safely represent grants across the multiple resource types this system actually has (doc-store spaces/pages, repo connections, onboarding-plan/hire visibility), each with its own ID space; a bare scope value has no way to say which one it belongs to. `resource_type` is an enum (`doc_space`, `repo_connection`, `onboarding_hire`, plus a `global` sentinel covering everything Phase 0 actually grants against), `resource_id` a generic identifier interpreted per type. This is what actually delivers the "no future migration" property the single-column design only claimed to: adding a new finer-grained resource type in Phase 2 means adding an enum value and populating rows, not restructuring the grants table. A dedicated policy library (e.g., Casbin) is deferred until Phase 2 actually needs it; a straightforward grants table plus middleware check is sufficient at MVP.

Top alternative considered: **code-host OAuth (GitHub/GitLab Sign-In) as the sole auth mechanism.** Rejected outright as the exclusive path — it directly violates the requirement that doc-store access be independent of the code host's account system, since HR/People staff without a code-host seat couldn't log in at all. Still offered as one OIDC-compatible option among several for engineers who prefer it, just never the only path. (Standalone local password, considered and now rejected in favor of magic-link-only, is covered above rather than here since it wasn't a full alternative to the whole approach — just to the fallback mechanism within it.)

## 7. Search

**Pick: Postgres full-text search (`tsvector`/`tsquery` + `pg_trgm` for fuzzy matching), with results filtered by caller permissions at query time from the start. Phase 0 covers doc-store content only; Phase 1 extends the same corpus and the same permission-filtering rule to indexed repo-doc content, delivering "search across both doc sources" (overview §6) — not a separate search system. Graduate to Meilisearch (using its tenant-token filtering) if/when corpus size or relevance needs outgrow it.**

- At the self-hosted, single-instance scale this product targets (a handful of connected repos' docs plus one internal wiki), Postgres FTS comfortably covers search without adding another stateful service to the docker-compose deployment. Doc-store search ships in Phase 0 since it's structurally tied to the doc-save flow (§4); repo-doc content joins the same corpus in Phase 1 (5.4).
- Doc content indexed in the same database as the source rows stays transactionally consistent with no separate indexing pipeline or lag to manage at MVP.
- **Query-time permission filtering is a required part of the pick, not an add-on.** Search that isn't filtered by the caller's `(user, role, resource_type, resource_id)` grants (§6) is a well-documented failure mode — indexed content silently outlives whatever permission state it was indexed under, letting search surface things the direct-read path would deny (real-world precedent: enterprise search deployments that exposed legal/deal-room documents and healthcare records this way because permission checks lived at index time instead of query time). Every search query must therefore carry a `WHERE (resource_type, resource_id) IN (caller's current allowed resources)` predicate evaluated in the same query as the text match, sourced from the live grants table — never a permission snapshot cached at index time. Each indexed row is tagged with the `(resource_type, resource_id)` of the doc-space or repo it belongs to, not a bare scope value, so the filter can distinguish "grants access to this doc space" from "grants access to this repo" instead of comparing values from different ID spaces as if they were interchangeable. When a page's resource grant changes, the very next search for it must reflect that; there is no "the index will catch up eventually."
- **The indexed corpus must eventually include actual repo-documentation content, not just ingestion's derived signals — this is the Phase 1 half of the feature.** The repo-ingestion pipeline (§5) computes commit/blame stats and expertise scores in Phase 0 — none of that is document *text*. "Search across both doc sources" (overview §6, Phase 1) requires an explicit step that reads a configurable set of documentation paths per repo connection (e.g. `README.md`, `/docs`) — via the host content API or the local clone already made for blame/churn — and writes that text into the same search corpus as doc-store content. Scoped to designated doc paths, not the whole codebase, so this stays "search over docs" rather than turning into general code search, which nothing in the overview asks for. Each indexed repo-doc row carries the same scope/permission linkage as the rest of the corpus, so the query-time filter above applies uniformly to both sources the moment this ships — permission filtering is not something to retrofit onto repo-doc content later, it's built the same way from the day this Phase 1 piece lands.
- **Text search configuration is a decision to make explicitly, not leave defaulted.** Postgres's default `english` configuration applies stemming and stop-word rules tuned for prose; repo docs will contain code-shaped content (camelCase/snake_case identifiers, file paths, error strings) that config doesn't tokenize well. Evaluate against real repo-doc content before committing to `english` vs. `simple` vs. a custom configuration — a lower-severity tuning call than the two points above, but one the doc shouldn't silently inherit Postgres's default for.
- **Growth path (Phase 2, "Comfort & Scale"): Meilisearch**, not Elasticsearch/OpenSearch. Meilisearch is a single lightweight binary purpose-built for "add a good self-hosted search box," fits the docker-compose model, and gives typo-tolerant, relevance-ranked results with minimal integration work. Carry the permission-filtering requirement forward using Meilisearch's native **tenant tokens** (API keys scoped with a query filter, built for exactly this "each caller sees only their allowed slice" case) rather than re-deriving access control from scratch on the new engine.

Top alternative considered: **Elasticsearch/OpenSearch**, even as the future option. Rejected — JVM-heavy, cluster-oriented operational model is disproportionate to a single company's cold_start data volume and works against the self-hosted, low-operational-burden target (§8). Not justified at any phase this project currently plans for.

## 8. Deployment

**Pick: docker-compose as the primary and default self-hosted deployment target**, matching the overview's non-goal that multi-tenant SaaS is out of scope for v1 (one instance per company).

Suggested service topology:

| Service | Role |
|---|---|
| `app-backend` | Go binary: API, auth, ingestion workers (webhook receiver + scheduled polling), doc-store git operations. Runs ingestion as an in-process worker pool at MVP — no separate queue/worker service until ingestion volume actually demands horizontal scaling. |
| `app-frontend` | Next.js, standalone build output, single container. |
| `postgres` | Primary DB + MVP full-text search. |
| reverse proxy | Caddy — see the TLS note below; the choice over Traefik still holds, but the "automatic HTTPS with minimal config" justification needs a caveat. |
| outbound email (external, not self-hosted) | Not a container in this topology — an operator-supplied SMTP-compatible relay/provider, configured as credentials on `app-backend`. Required for magic-link delivery (§6); self-hosting an email server is explicitly out of scope for this stack. |
| backup job (new) | Scheduled, not a long-running service: a periodic job (cron container or host-level cron calling into the compose stack) that produces a coordinated `pg_dump` + `git bundle` pair — see backup note below. Ships to off-host storage the operator controls; this stack doesn't include or mandate a specific destination. |

Volumes: one for Postgres data, one for the `go-git`-managed bare repo(s) backing the doc store (persistent, backed up), one scratch volume for ephemeral code-repo clones used in ingestion (safe to wipe/recreate, never a source of truth).

**TLS note — Caddy's automatic-HTTPS justification assumes reachability that isn't guaranteed here.** Caddy's default ACME challenges (HTTP-01, TLS-ALPN-01) require Let's Encrypt to reach the server on port 80/443 from the public internet. That's the same reachability assumption already shown not to hold for a lot of realistic deployments of this stack (§5 — companies self-host specifically to stay off the public internet, which is exactly the case where GitHub-hosted webhooks also can't be delivered). So the actual reason Caddy was picked over Traefik doesn't work out of the box for that deployment shape. Three cases, stated explicitly instead of assumed:
- **Public ingress available:** HTTP-01/TLS-ALPN-01 work as originally described, zero extra config.
- **Internal-only, with a supported DNS provider:** use Caddy's DNS-01 challenge — no open ports needed, since Caddy proves domain ownership by writing a TXT record via the provider's API instead of serving a challenge over the internet. Requires a Caddy build that includes the matching DNS-provider plugin (not in Caddy's default build) plus that provider's API credentials as a secret — a real dependency to name, not a given.
- **Internal-only, no supported DNS provider:** fall back to Caddy's local/internal CA. This isn't "automatic" in the same sense — every client browser/OS needs that CA's root certificate installed manually to trust it, which is an operator rollout task, not something the stack does for them.

**Backup note — the two irreplaceable volumes must be backed up together, not independently.** `pg-data` and `docstore-data` were previously just named as "must be backed up," but a single doc save writes to both in sequence (architecture doc §3.2: a git commit to the doc-store repo, then a Postgres metadata/search-index row update in the same request). Backing the two volumes up on separate, uncoordinated schedules risks a restore that mixes two different points in time: Postgres rows pointing at doc-store commits absent from the restored git backup, or git commits with no corresponding metadata row. The backup job above produces both artifacts (`pg_dump` and `git bundle`) from the same coordinated run so a restore always pairs a consistent snapshot of each — this is now treated as a correctness requirement of the backup step, not an implementation detail left to the operator.

Top alternative considered: **Kubernetes/Helm chart as the primary target.** Rejected as the *default* path — it raises the operational bar for the actual buyer (one company standing up one instance) well above what's justified at this scale. A Helm chart remains a reasonable optional offering later for companies already running k8s, but docker-compose is the on-ramp new adopters should hit first.
